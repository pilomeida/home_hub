## 2026-10-16 — D18. The ratchet: a run's level only rises (Pedro's rule; mechanism by Claude)
- **One way.** A run (an Ask question, the weekly wiki check, an intake read) has a level. It rises to High the moment a tool returns content of a private type, and every later call the run makes goes out at High only, until the run ends. It never falls, and nothing an explicit level says can lower it. Built in `app/privacy/ratchet.py` (`ratchet_scope`, `apply_ratchet`); the gateway applies it to every call (`app/llm_gateway.py`).
- **The person is told** what was opened, at which step, and that nothing went to another AI service afterwards (the "This answer turned private" notice on the answer, `app/services/ask/private.py`).
- **The first call is blind to private content.** It is built from `Reach.without_private()`: no private record is named, counted or summarised in it. Tools use the full reach and raise the run.
- **Every tool that returns private content reports `tier=HIGH`**, including when nothing matches (the Health tools always do), so the rise is recorded even when the answer is empty.
- **A chat that has had a private answer starts every later answer High**, because the replayed history carries that content. An answer that cites a source now private counts too.
- **Private answers are not saved to the wiki** (`app/services/ask/save.py`), and they are shown only in the Hub, never in Telegram or email.
- **Fails closed.** A run's stored log (`AskTurn.escalation_json`) is read by `RatchetLog.from_json`. A non-empty log that does not parse reads as private, so a damaged record never opens a lower level.

## 2026-10-15 — D16. Ask and the wiki check under levels (built; coordinator's rules, Claude's mechanism)
Closes known gap (1) of D13. **Only when "Levels are binding" is on; with it off both behave, and send, exactly as before (checked byte-for-byte against the previous code).**
- **Reachable set** (`app/privacy/reach.py`, snapshot taken when a run starts): a document type is **left out** if its level is High, or it has no level, or its "hide personal details" switch is on (hiding cannot work when the AI also looks things up or reads files). Every other type is **readable**. The level of every AI call is the **strictest level among the readable types** (Low < Mid); with none readable, Mid is the floor. A document whose category is not a registered type counts as "no level".
- **Entered where it runs:** `reachable_scope(session)` (in `app/privacy/scope.py`) is entered inside `run_turn` (Ask) and `execute_run` (wiki check), i.e. inside the background task with its own session; it reuses the existing scope variable, so the gateway client adds the level with no other change.
- **What is filtered** (the AI never sees it): `find_sources`, `read_document_file` (a withheld file answers exactly like a missing one), `read_wiki_pages`, `list_todos`, the Financials tools (transactions follow the document they were read from), the system prompt (domain counts, wiki index, the "waiting in the Inbox" count, which uses the Inbox's suggested type), earlier answers of the same chat, and the wiki check's pages, claims and sources. A wiki claim is hidden if **any** of its current sources is left out; a page whose claims are all hidden is hidden (a hidden page reads as "not found"); a page with some hidden claims keeps its readable claims but its stored summary (which may repeat the hidden ones) is rebuilt from them. Claims and pages with no document source (saved Ask answers) stay readable. A record follows its own type; a record's attached file must be of a readable type too.
- **Earlier answers in a chat:** an answer written while levels were off, or before a type was left out, may repeat details from it, so it is not sent back to the AI; the answer's page says so. (Follow-ups after switching levels on therefore start without the earlier answers once.)
- **What the person sees (messages rule):** each Ask answer and each wiki-check run says "N documents weren't available to this answer/check", why (per type: set to High / no level yet / hides personal details) and what to do (Privacy page). The check also logs it in the Problems log (cleared by the first run that leaves nothing out) and its job result becomes "partly done". The model is told that its records are incomplete. Ask's own failures (AI unreachable, refusal, no answer, too many look-ups, unexpected error) now follow the same three-part rule, with the raw text kept under "Technical details"; an unexpected error no longer leaves a question "thinking" forever.
- **Storage:** `ask_turns.left_out_json`, `lint_runs.left_out_json` (migration d4a8c6e2b715, additive).
- **Known gaps:** a saved Ask answer written while levels were off can contain details of a type that is later left out and stays readable (it has no document source); the titles of wiki pages made from a left-out document can still reach a *filing* call of another type in the same domain (the wiki "existing pages" list at ingest); the Inbox AI suggestion is still unscoped.

## 2026-10-15 — D13. Recognising documents: known ones automatic, new ones ask (Pedro; mechanism by Claude)
- **Known, recurrent documents** are recognised without any AI, by fingerprints the Hub holds: sender address (email/Telegram sender), issuer words in the PDF's own text layer, filename pattern, account/contract number already on file. A match assigns the document type and therefore the tier, and the document proceeds.
- **New or unrecognised documents** stop at a "What is this?" card with the list of types (including "Sensitive: don't read it") before anything reads them. Choosing a type sets the tier; the card then offers "Remember this for next time" (on by default), which stores a new fingerprint.
- **Scans and photos have no text layer to fingerprint**, so most go the "What is this?" route unless the sender or caption identifies them. Nothing is sent to any AI until the type (and so the tier) is known. This also removes a chicken-and-egg: today the classifier sends the raw file to a model to decide what it is, before any tier exists.
- Optional later: for text PDFs only, a mid-tier (zero-retention, US/EU, redacted) suggestion to pre-select the type on the card. Not built unless Pedro asks.

## 2026-10-15 — D14. Messages for what could not be done (Pedro)
**Rule:** every warning or error a person can see says three things, in this order — *what* didn't happen ("Not uploaded."), *why* (the reason, in plain words), and *what they can do*. A fact without its reason, or a reason without a way forward, is a defect. Technical text is kept, but only as a collapsed "Technical details" for whoever has to dig.
- **Built (`app/problems.py`):** the three-part `Problem`; `classify_reason()` turns technical causes (AI service down, out of credit, no model allowed, unreadable PDF, too big, privacy blocks, hiding-details blocks, invalid values) into fact/why/next; `for_http()` does the same for every web error (all 51 `HTTPException` sites are covered by one central handler, plus routes can pass their own message).
- **How it is shown:** a full page for a browser; a red banner at the top of the page for a button press (HTMX); the original JSON for API-style callers (unchanged). **Found and fixed:** HTMX silently ignores error responses by default, so a failed Approve/Save click showed nothing at all; failed presses now always show a message, including "the Hub couldn't be reached" and "took too long".
- **The Problems page (`/problems`, count in the menu):** things that failed where nobody was looking are logged with area, reason, next step and technical details: documents that couldn't be processed, scheduled jobs that failed, email that wasn't filed (unknown forwarder, no usable attachment, unreadable, error), Telegram files that weren't saved and messages from people not on the list (the stranger still gets no reply). A problem clears itself when the thing works (document processed, job succeeds) or can be dismissed.
- **Converted so far:** web errors (all), stored document failures (`friendly_reason` now = fact + why + next step), Telegram replies, email intake, scheduled jobs, the privacy hold (uploads and Inbox), upload errors, to-dos. **Converted in the follow-up batches (2026-10-15):** bank sync and bills (with per-account/per-connection entries on the Problems page), the statement reminder, loans and utilities pages, transactions/house/insurance/documents/to-dos/wiki check, Ask's in-answer errors. **Still open:** short field-level hints in `app/domains/fields.py` ("Choose a category"), the import script's `--dry-run` REJECTED line, and any new feature must follow the rule from the start (written into `CLAUDE.md`).

## 2026-10-15 — D15. Schedules are settings on the Hub (Pedro)
- **Page `/schedules`:** one page for background jobs. Options: every day; every N days; every week on a chosen day (so "every Monday"); every N weeks on a chosen day; every month on a chosen date (clamped to short months); several fixed times a day; every N minutes; plus time of day (Lisbon time) and on/off, a "Run now" button, last result in plain language, next run, and recent runs.
- **Mechanism:** one systemd user timer (`home-hub-scheduler.timer`, every 5 minutes, on the clock) starts `app.jobs.scheduler`, which runs the jobs that are due according to the schedules saved in the database. No server edits are ever needed to change a schedule. A run missed because the server was off happens once, at the next check; a manual run never moves the cycle; two runs of one job can't overlap; a crash becomes a plain-language result and a Problems entry, never a silent failure.
- **Onboarded:** the wiki check (default: Sundays 04:30 Lisbon, as before; the first scheduled run honours the last run of the old timer so nothing re-runs at once), and, since 2026-10-15, **bank sync** (default 07:30, 13:00, 18:30 Lisbon), **statement reminder** (default daily 09:00; it still sends only when a reminder is due) and **mailbox check** (default every 10 minutes). The old fixed timers `home-hub-wikilint`, `home-hub-banksync`, `home-hub-reminder` and `home-hub-mailpoll` are retired by the deploy script; nothing is left on a fixed timer, so the page no longer has a "still on fixed timers" section. The weekly "things to check" Telegram nudge (D11) will be born on the same mechanism.
- **Two schedule kinds added for them:** *several times a day* (fixed Lisbon times, stored comma-separated in the existing `time_of_day` column, so no migration) and *every N minutes* (5 to 1440, counted from the start of the last scheduled run). Same guarantees as the rest: a missed run happens once, a manual run never moves the cycle, and the clock change in Lisbon is handled (moments are compared as real instants).
- **Daily limit per job:** a job may declare the most runs a day it can take. Bank sync declares 4 (the bank allows 4 requests per account per day); the Hub refuses to save a schedule that could exceed it, in three parts (what, why, what to do). The bank-call ledger (`bank_api_calls`, 4 per account per rolling 24 h) still stops a 5th request whatever the schedule says, and “Sync now” on the bank page shares that allowance.
- **Timing:** the scheduler checks every 5 minutes, so a job starts at most about 5 minutes after its planned moment (the check is on the clock, so a 07:30 slot starts at about 07:30). A job that is still running (a long bank sync) is never started again by the next check, and jobs run one after another, quick ones first.
- **Infrastructure change (second, disclosed):** the scheduler timer goes from every 15 to every 5 minutes; three more fixed timer/service pairs are retired.
- **Infrastructure change (disclosed):** one new timer/service pair on the server and one retired; installed by the normal deploy.

## 2026-10-14 — D10. Provider retention findings (verified 2026-10-14)
- **OpenRouter** (docs: provider routing; ZDR guide): `provider.zdr: true` restricts routing to endpoints with a zero-data-retention policy; `provider.data_collection: "deny"` excludes providers that may store/train on data. A request can only switch ZDR on, never off an account/guardrail setting. Endpoints with unclear policy are treated as retaining. Public list: `GET /api/v1/endpoints/zdr`. Caveats: ZDR covers model inference only (not plugins/web-search tools); implicit in-memory caching is not counted as retention; the docs do not state the error returned when no ZDR endpoint exists (expect a 404 "no endpoints"; the call fails, it is never retried without the flag). The "Data Policy" tags are OpenRouter's best knowledge, not a third-party guarantee.
- **GLM 5.3 Flash on OpenRouter:** the live ZDR list has ~29 endpoints for it; 7 pass the gateway's quantisation floor (fp8): BaseTen, Inceptron, Near AI, SiliconFlow, Morph, Novita, Z.AI. So the Hub's current model can serve house_mid. With the US/EU rule (D8) the usable ones are BaseTen, Morph, Inceptron (SE) and Novita; Z.AI and SiliconFlow (declared SG) and Near AI (no declared HQ) are excluded.
- **Nous Portal** (portal.nousresearch.com/privacy): no fixed retention period for API prompts/outputs. Without "Privacy Mode" prompts and outputs may be shared with third parties and used to train/fine-tune. "Privacy Mode" (account setting) says inference payloads are not stored or used for training, with security/legal/fraud exceptions; it is prospective only. No zero-data-retention product is described, and Nous's API rejects any per-request privacy parameter. Conclusion: Nous stays out of house_mid and house_high; at most house_low.
- **house_high route (future):** nothing exists yet. Dedicated capacity (e.g. Mistral) would need its own adapter and a verified per-request or contractual guarantee before it is added to `ZDR_ENFORCEABLE_PROVIDERS`-style allow-listing.

## 2026-10-14 — D4. Redactor design (Claude)
Detection is by shape + checksum (IBAN mod-97, NIB check digits, Luhn, NIF check digit), plus a lookup of values the Hub already knows (family names and name parts, addresses, policy/contract and account numbers). Rationale: no model is involved, so nothing leaves the VPS to find what to hide; checksums keep ordinary numbers (amounts, invoice refs) from being redacted. Over-redaction is the safe failure: a 9-digit number starting 2 or 9 may be labelled PHONE instead of NIF; it is hidden either way. Known limit: a value the Hub has never seen (a stranger's name, a free-text address) cannot be caught — which is why redaction is an extra layer on top of the tier's endpoint rule, not the rule itself.
After redacting, the output is re-scanned; anything still detectable, or any redactor error, blocks the call (`TierBlocked`).

## 2026-10-14 — D5. Vault and key (Claude)
One vault per session; same value, same placeholder, even if written differently (spaced vs unspaced IBAN). Restore puts back the first spelling seen. The mapping can be sealed with Fernet (authenticated encryption) using `HUB_PRIVACY_KEY` from the server's `.env`; wrong or missing key = error, never plaintext fallback. The key must be created and added to the VPS `.env` before sealed vaults are stored (not needed until phase c/d wires a call site).
